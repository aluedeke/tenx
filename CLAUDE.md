# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tenx` is a CLI + TUI tool (Rust) that manages multi-repo "workspaces" and "tasks". A workspace holds one or more bare git repos; a task is a named unit of work that creates a git worktree (on a branch matching the task's slug) in each of the workspace's repos, then opens a zellij tab with a claude/nvim/shell layout for that task. It also drives a Claude Code integration layer of its own (hooks, skills, tab notifications) and a `standup` command that summarizes recent Claude Code activity — so this tool is itself part of the harness a Claude Code session runs inside when working in a `tenx`-managed task.

## Commands

```sh
cargo build --release   # build (Makefile `build` target does this)
cargo build              # debug build, faster iteration
cargo run -- <args>       # run without installing, e.g. `cargo run -- task list`
cargo check               # fast type-check without producing a binary
make install              # builds release and installs to $PREFIX/bin (default ~/.local/bin)
```

There is no test suite in this repo (no `#[test]` items) and no CI config. There is no lint config beyond default `cargo` — use `cargo clippy` if checking lint issues. `Cargo.lock` is checked in.

## Architecture

Independent layers wired together by `main.rs`'s CLI dispatch; each layer only knows about the layer(s) below it:

- **`cli/`** — clap-based argument parsing (`mod.rs`) plus one file per subcommand group: `init.rs`, `repo.rs`, `task.rs`, `standup.rs`, `hooks.rs`, `tab.rs`. These are the actual command implementations — `main.rs` matches on the parsed `Commands` enum and calls into them. The TUI (`tui/app.rs`, `tui/repos.rs`) calls directly into these same functions (`cli::task::{new,open,rm}`, `cli::task::install_hooks`) instead of duplicating logic.
- **`workspace/`** — the on-disk model. A *workspace* is a directory with a `config.toml` (name, layout path, list of repos) and a `tasks/` subdirectory; each subdirectory under `tasks/` is a *task*. `workspace::find()` walks up from cwd looking for `config.toml`, so commands work from any subdirectory of a workspace. Global user config lives at `~/.config/tenx/config.toml` (currently just a `bare_dir` override). Config writes are atomic (write to `.toml.tmp`, then rename).
- **`git/`** — shells out to the system `git` CLI for everything (bare clone, fetch, worktree add/remove, default-branch detection) rather than using a git library, specifically so SSH agent / credential helpers behave the same as the user's normal `git` invocations. Bare repos live under `<workspace>/../.bare/<name>.git` by default, or under the global `bare_dir` override if set. `ensure_synced()` clones if the bare repo doesn't exist yet or fetches if it does — this is the entry point task creation uses.
- **`github.rs`** — wraps the `gh` CLI (not the GitHub API directly) to list open PRs for a repo and get the current authenticated user. Used by the repos TUI to show PR counts/lists per repo.
- **`progress.rs`** — a threaded spinner (`Spinner::new(label)` → `.done()`/`.fail(err)`) used to show progress during clone/fetch/worktree operations without letting raw git output bleed into the terminal.
- **`zellij/`** — shells out to the `zellij` CLI to manage sessions and tabs. Session names are `tenx:<slugified-workspace-name>`. `find_bin()` searches common install locations (`~/.cargo/bin`, `~/.local/bin`, `/opt/homebrew/bin`, etc.) rather than trusting `$PATH`, since hook scripts invoke `zellij`/`tenx` from arbitrary CWDs. The top-level session layout (`full_session_layout`) is a single "tenx" tab split into two panes: `tenx tasks` (task-list TUI, 65%) and `tenx repos` (repos TUI, 35%). Task tabs get their own layout — either the workspace's configured layout file or the built-in default (claude/nvim/shell split, with nvim opened on `TASK.md`). Tabs are tracked by *stable numeric tab_id* (not just name), since tab names change (see tab notifications below) and can collide.
- **`tui/`** — ratatui/crossterm terminal UIs. `mod.rs` wires the event loop; `app.rs` holds task-list state/mutations (`View::List`/`View::Create`, create-task popup with per-repo checkboxes, delete confirmation); `ui.rs` is pure rendering for the task list; `repos.rs` (~770 lines) is a separate, self-contained TUI for browsing workspace repos — clone status, last commit, and cached-with-background-refresh PR counts/lists via `github.rs`, with a "mine only" filter and the ability to open a PR in the browser. `tui::run()` (task list) and `tui::run_repos()` are both invoked as zellij pane commands (`tenx tasks`, `tenx repos`), not as a single combined TUI.

## Key flows to understand together

- **No-argument / `tui`/`tasks` invocation** (`open_workspace()` in `main.rs`): finds the enclosing workspace from cwd and computes the expected zellij session name. If already inside that session, it runs the task-list TUI **directly in the current pane** (not by switching tabs). If inside a *different* zellij session, it refuses rather than clobbering it. If outside zellij entirely, it attaches to the session if it exists, or creates it via `zellij --new-session-with-layout` using a layout file written to `~/.config/zellij/layouts/` (required because `--layout-string`/`--layout` only append tabs to an existing session, they don't produce a clean fresh session).
- **Task creation** (`cli::task::new`): slugifies the task name (`workspace::slugify` — lowercase, spaces/underscores → dashes) for the directory/branch name but keeps the original `name` as the task's *display name*. Writes a `TASK.md` template (`# <display name>` header + Description/Todo/Links/Notes sections) and ensures workspace-level `.claude/settings.json` + hook scripts exist, then symlinks `tasks/<slug>/.claude → ../../.claude` so Claude Code discovers workspace hooks/skills from inside the task directory. For each repo: `ensure_synced` (clone-or-fetch) then `git worktree add` off the detected default branch if the task's branch doesn't already exist. Finally opens a zellij tab (unless `--no-open`) and records the new tab's stable `tab_id` in `tasks/<slug>/.tenx-tab-id`.
- **Task display name vs. slug**: `workspace::discover_task` derives `display_name` by reading the first line of `TASK.md` (falling back to the directory name), while `name`/branch/directory all use the slug. `cli::task::open` uses the stored `.tenx-tab-id` to find the tab directly (fast path); if the TASK.md title changed since the tab was created, it renames the tab to match before switching. If the stored id is stale (tab closed, or a new zellij session), it's simply treated as not-open.
- **Claude Code integration is bidirectional**: `tenx init` optionally installs two skills into the workspace's `.claude/skills/` — `/tenx` (`src/cli/skills/tenx.md`, describing workspace layout, the boundary that a Claude session should only edit inside its own `tasks/<name>/`, and the TASK.md conventions to maintain) and `/standup` (a const string in `init.rs` describing how to run `tenx standup` and format the result into `daily.local.md`). Separately, `tenx init`/`task new` write `.claude/settings.json` hooks (`Stop` → `tenx tab notify`, `UserPromptSubmit` → `tenx tab notify-clear`) so a task's zellij tab gets a 💬 indicator while Claude is actively working. `tenx hooks install` re-writes these hook scripts (e.g. after upgrading the tenx binary, since the scripts embed an absolute path to it).
- **`tenx standup`** (`cli::standup`): reads every task's `TASK.md` verbatim (authoritative source for PR/Linear links) plus parses `~/.claude/projects/<slug>*/*.jsonl` Claude Code session logs — filtering to user messages and `git commit`/`git push` bash tool calls since the last standup (tracked via a `<!-- last-standup: ... -->`-adjacent heading in the workspace's `daily.local.md`, or defaulting to the start of yesterday). Project slugs are matched by replacing `$HOME` and `/` with `-` in the workspace path, so any Claude Code project whose path is under this workspace is picked up. This raw output is meant to be fed to the `/standup` skill, not read directly by users.
