# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tenx` is a CLI + TUI tool (Rust) that manages multi-repo "workspaces" and "tasks". A workspace holds one or more bare git repos; a task is a named unit of work that creates a git worktree (on a branch matching the task's slug) in each of the workspace's repos, then opens a claude/nvim/shell layout for that task inside the single global zellij session. It also drives a Claude Code integration layer of its own (hooks, skills, attention notifications) and a `standup` command that summarizes recent Claude Code activity — so this tool is itself part of the harness a Claude Code session runs inside when working in a `tenx`-managed task.

## Commands

```sh
cargo build --release   # build (Makefile `build` target does this)
cargo build              # debug build, faster iteration
cargo run -- <args>       # run without installing, e.g. `cargo run -- task list`
cargo check               # fast type-check without producing a binary
make install              # builds release and installs to $PREFIX/bin (default ~/.local/bin)
```

There is no test suite in this repo (no `#[test]` items) and no CI config. There is no lint config beyond default `cargo` — use `cargo clippy` if checking lint issues. `Cargo.lock` is checked in.

## Architecture

Independent layers wired together by `main.rs`'s CLI dispatch; each layer only knows about the layer(s) below it:

- **`cli/`** — clap-based argument parsing (`mod.rs`) plus one file per subcommand group: `init.rs`, `repo.rs`, `task.rs`, `standup.rs`, `hooks.rs`, `tab.rs`. These are the actual command implementations — `main.rs` matches on the parsed `Commands` enum and calls into them. The overlay TUI calls directly into these same functions (`cli::task::{new_in,open_in,rm_in,set_repos_in}`, `cli::repo::add_in`) instead of duplicating logic; the overlay *plugin*, which can't link against them, shells out to the equivalent `--ws-dir` subcommands.
- **`workspace/`** — the on-disk model. A *workspace* is a directory with a `config.toml` (name, layout path, list of repos) and a `tasks/` subdirectory; each subdirectory under `tasks/` is a *task*. `workspace::find()` walks up from cwd looking for `config.toml`, so commands work from any subdirectory of a workspace. Global user config lives at `~/.config/tenx/config.toml` (currently just a `bare_dir` override). The workspace *registry* is one file per workspace under `~/.config/tenx/workspaces.d/<name>-<pathhash>.toml` (content: `path = "..."`) — registration is a single atomic file write so concurrent tenx invocations can't lose entries, and pruning dead workspaces is a per-file delete; a legacy single-file `workspaces.toml` is imported and removed on first read. Config writes are atomic (write to `.toml.tmp`, then rename).
- **`git/`** — shells out to the system `git` CLI for everything (bare clone, fetch, worktree add/remove, default-branch detection) rather than using a git library, specifically so SSH agent / credential helpers behave the same as the user's normal `git` invocations. Bare repos live under `<workspace>/../.bare/<name>.git` by default, or under the global `bare_dir` override if set. `ensure_synced()` clones if the bare repo doesn't exist yet or fetches if it does — this is the entry point task creation uses.
- **`progress.rs`** — a threaded spinner (`Spinner::new(label)` → `.done()`/`.fail(err)`) used to show progress during clone/fetch/worktree operations without letting raw git output bleed into the terminal.
- **`zellij/`** — shells out to the `zellij` CLI to manage the **single global session** `zellij::SESSION` (`"tenx"`) that holds every workspace's tasks. `find_bin()` searches common install locations (`~/.cargo/bin`, `~/.local/bin`, `/opt/homebrew/bin`, etc.) rather than trusting `$PATH`, since hook scripts invoke `zellij`/`tenx` from arbitrary CWDs. Layouts are **tabless**: no `zellij:tab-bar` anywhere (status-bar stays) — tasks live in zellij tabs purely as invisible state containers and the overlay is the only task list/switcher. The session layout (`home_layout`) is a single "home" tab running `tenx overlay --home` full-screen. Task tabs get their own layout — either the workspace's configured layout file or the built-in default (a 1-line header pane running `tenx tab header` — task name + live Claude status, re-read from `TASK.md`/`.tenx-status` every second — above a claude/nvim/shell split, with nvim opened on `TASK.md`). Layout templates may use the `{tenx}` placeholder for the absolute tenx binary path (PATH is unreliable in zellij-spawned commands), alongside `{name}`/`{cwd}`/`{claude_args}`. Tabs are tracked by *stable numeric tab_id*, with name matching as fallback (names are stable: set at creation, changed only by an explicit rename).
- **`tui/`** — the ratatui/crossterm overlay (`overlay.rs`, plus `mouse.rs` helpers): lists every task across every registered workspace with fuzzy filtering, create/delete/rename/close actions, and a lean Repos view. It runs in two modes: *home* (`tenx overlay --home`, the session's long-lived base pane — jumping switches tabs without exiting, quit keys are swallowed) and *floating* (`tenx overlay`, spawned by the tenx-zellij plugin on Ctrl+w — exits after a jump and the plugin closes the pane).
- **`tenx-zellij/`** — the Ctrl+w overlay, rendered natively as a wasm zellij plugin (see its module docs for why it's a plugin, not a launcher). It's the overlay users actually see, so **any task-management feature has to land here as well as in `tui/overlay.rs`** — the two are separate implementations of the same surface and drift easily. The sandbox has no filesystem, so all its data arrives as one JSON document from `tenx overlay --json` (`tui::dump_json`): a `tasks` array (what to list, plus each task's current repos) and a `workspaces` array (each workspace's configured repos and whether they're cloned), which together are what the repo checklists are built from. Every mutation shells back out to a `--ws-dir` subcommand; `run_mutation_busy` keeps the overlay up on a `Mode::Busy` while one runs, because a first clone can take minutes and an error needs somewhere visible to land.

## Key flows to understand together

- **No-argument invocation** (`open()` in `main.rs`): always connects to the single `tenx` session, regardless of cwd (if cwd is inside a workspace it self-heals the registry first). Inside the tenx session → runs the overlay **directly in the current pane**. Inside a *different* zellij session → switches the client in place via `zellij action switch-session` (passing `--layout` only when the session doesn't exist yet, so creation uses the home layout without appending tabs to an existing session). Outside zellij → attaches if the session exists, or creates it via `zellij --new-session-with-layout` using a layout file written to `~/.config/zellij/layouts/tenx.kdl` (required because `--layout-string`/`--layout` only append tabs to an existing session, they don't produce a clean fresh session).
- **Task creation** (`cli::task::new`): slugifies the task name (`workspace::slugify` — lowercase, spaces/underscores → dashes) for the directory/branch name but keeps the original `name` as the task's *display name*. Writes a `TASK.md` template (`# <display name>` header + Description/Todo/Links/Notes sections) and ensures workspace-level `.claude/settings.json` + hook scripts exist, then symlinks `tasks/<slug>/.claude → ../../.claude` so Claude Code discovers workspace hooks/skills from inside the task directory. For each repo in the chosen subset (`--repos`, default all): `ensure_synced` (clone-or-fetch) then `git worktree add` off the detected default branch if the task's branch doesn't already exist. Finally opens a zellij tab in the tenx session (unless `--no-open`; requires being inside that session) and records the new tab's stable `tab_id` in `tasks/<slug>/.tenx-tab-id`.
- **A task's repo set is derived from disk, never recorded**: `workspace::discover_task` builds `Task.repos` by scanning the task directory for subdirectories containing a `.git` *file* (a worktree). Nothing writes that list down, so adding or detaching a repo needs no bookkeeping — `task list`, both overlays, and `rm_in`'s cleanup loop all pick the change up for free. The verbs are `task add-repo` / `task rm-repo` (imperative) and `task set-repos` (declarative: reconcile to exactly this set, adding first so a failed clone can't leave the task half-detached). All three share `ensure_repo_worktree` with task creation, so a repo joining late gets the same treatment as one present from the start: a fresh branch named after the slug, off that repo's freshly-fetched default branch. Detaching removes the worktree *and* its task branch (same as `task rm` does per repo) and does **not** pass `--force` unless asked — git's refusal to drop a dirty worktree is the safety net, and both overlays rely on it rather than checking themselves.
- **Task display name vs. slug**: `workspace::discover_task` derives `display_name` by reading the first line of `TASK.md` (falling back to the directory name), while `name`/branch/directory all use the slug. `cli::task::open` uses the stored `.tenx-tab-id` to find the tab directly (fast path); if the TASK.md title changed since the tab was created, it renames the tab to match before switching. If the stored id is stale (tab closed, or the session was recreated), it's simply treated as not-open.
- **Claude Code integration is bidirectional**: `tenx init` optionally installs two skills into the workspace's `.claude/skills/` — `/tenx` (`src/cli/skills/tenx.md`, describing workspace layout, the boundary that a Claude session should only edit inside its own `tasks/<name>/`, and the TASK.md conventions to maintain) and `/standup` (a const string in `init.rs` describing how to run `tenx standup` and format the result into `daily.local.md`). Separately, `tenx init`/`task new` write `.claude/settings.json` hooks that all funnel through a single `event.sh` script → `tenx tab event` (`src/cli/tab.rs`), which reads the hook's JSON from stdin and maps `hook_event_name` to a task *state* written to the `.tenx-status` file in the task dir. The phase-1 hook set is `SessionStart`/`SessionEnd`/`UserPromptSubmit`/`Notification`/`Stop`/`StopFailure`, mapping to the `TaskStatus` enum (`src/workspace/mod.rs`): `working` (UserPromptSubmit / tool calls), `blocked` (a "needs you" Notification — permission/idle/needs-input), `done` (Stop), `failed` (StopFailure), `idle` (SessionStart; SessionEnd clears the file). The event→state mapping lives in Rust, so adding events is a code change, not a settings.json edit. The overlay renders each state with its own glyph (💬 blocked / ✅ done / ⚠️ failed / ▷ working; tab names are never touched). `tenx hooks install` re-writes the hook script/settings (e.g. after upgrading the tenx binary, since the script embeds an absolute path to it) and removes the pre-`event.sh` `notify.sh`/`notify-clear.sh` scripts.
- **`tenx standup`** (`cli::standup`): reads every task's `TASK.md` verbatim (authoritative source for PR/Linear links) plus parses `~/.claude/projects/<slug>*/*.jsonl` Claude Code session logs — filtering to user messages and `git commit`/`git push` bash tool calls since the last standup (tracked via a `<!-- last-standup: ... -->`-adjacent heading in the workspace's `daily.local.md`, or defaulting to the start of yesterday). Project slugs are matched by replacing `$HOME` and `/` with `-` in the workspace path, so any Claude Code project whose path is under this workspace is picked up. This raw output is meant to be fed to the `/standup` skill, not read directly by users.
