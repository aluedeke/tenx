# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tenx` is a CLI + TUI tool (Rust) that manages multi-repo "workspaces" and "tasks". A workspace holds one or more bare git repos; a task is a named unit of work that creates a git worktree (on a branch matching the task's slug) in each of the workspace's repos, then opens a claude/nvim/shell layout for that task inside the single global zellij session. It also drives a Claude Code integration layer of its own (skills, plus live task state read from Claude Code's session registry) and a `standup` command that summarizes recent Claude Code activity — so this tool is itself part of the harness a Claude Code session runs inside when working in a `tenx`-managed task.

## Commands

```sh
cargo build --release   # build (Makefile `build` target does this)
cargo build              # debug build, faster iteration
cargo run -- <args>       # run without installing, e.g. `cargo run -- task list`
cargo check               # fast type-check without producing a binary
make install              # builds release and installs to $PREFIX/bin (default ~/.local/bin)
```

There is no test suite in this repo (no `#[test]` items) and no CI config. There is no lint config beyond default `cargo` — use `cargo clippy` if checking lint issues. `Cargo.lock` is checked in.

## Architecture

Independent layers wired together by `main.rs`'s CLI dispatch; each layer only knows about the layer(s) below it:

- **`cli/`** — clap-based argument parsing (`mod.rs`) plus one file per subcommand group: `init.rs`, `repo.rs`, `task.rs`, `standup.rs`, `hooks.rs`, `watch.rs`. These are the actual command implementations — `main.rs` matches on the parsed `Commands` enum and calls into them. The overlay TUI calls directly into these same functions (`cli::task::{new_in,open_in,rm_in,set_repos_in}`, `cli::repo::add_in`) instead of duplicating logic; the overlay *plugin*, which can't link against them, shells out to the equivalent `--ws-dir` subcommands.
- **`workspace/`** — the on-disk model. A *workspace* is a directory with a `config.toml` (name, layout path, list of repos) and a `tasks/` subdirectory; each subdirectory under `tasks/` is a *task*. `workspace::find()` walks up from cwd looking for `config.toml`, so commands work from any subdirectory of a workspace. Global user config lives at `~/.config/tenx/config.toml` (currently just a `bare_dir` override). The workspace *registry* is one file per workspace under `~/.config/tenx/workspaces.d/<name>-<pathhash>.toml` (content: `path = "..."`) — registration is a single atomic file write so concurrent tenx invocations can't lose entries, and pruning dead workspaces is a per-file delete; a legacy single-file `workspaces.toml` is imported and removed on first read. Config writes are atomic (write to `.toml.tmp`, then rename).
- **`git/`** — shells out to the system `git` CLI for everything (bare clone, fetch, worktree add/remove, default-branch detection) rather than using a git library, specifically so SSH agent / credential helpers behave the same as the user's normal `git` invocations. Bare repos live under `<workspace>/../.bare/<name>.git` by default, or under the global `bare_dir` override if set. `ensure_synced()` clones if the bare repo doesn't exist yet or fetches if it does — this is the entry point task creation uses.
- **`progress.rs`** — a threaded spinner (`Spinner::new(label)` → `.done()`/`.fail(err)`) used to show progress during clone/fetch/worktree operations without letting raw git output bleed into the terminal.
- **`zellij/`** — shells out to the `zellij` CLI to manage the **single global session** `zellij::SESSION` (`"tenx"`) that holds every workspace's tasks. `find_bin()` searches common install locations (`~/.cargo/bin`, `~/.local/bin`, `/opt/homebrew/bin`, etc.) rather than trusting `$PATH`, since `tenx` is invoked from arbitrary CWDs (zellij-spawned panes, layout commands). Layouts are **tabless**: no `zellij:tab-bar` anywhere (status-bar stays) — tasks live in zellij tabs purely as invisible state containers and the overlay is the only task list/switcher. The session layout (`home_layout`) is a single "home" tab running `tenx overlay --home` full-screen. Task tabs get their own layout — either the workspace's configured layout file or the built-in default (a claude/nvim/shell split with nvim opened on `TASK.md`). Every layout carries the `tenx-statusbar` plugin as its `default_tab_template` bar: layout templates get it from the `{statusbar}` placeholder, and any layout still naming `zellij:status-bar` is rewritten to it by `render_layout`, so files living outside this repo gain the bar without being edited. Templates may also use `{tenx}` for the absolute tenx binary path (PATH is unreliable in zellij-spawned commands), alongside `{name}`/`{cwd}`/`{claude_args}`. Tabs are tracked by *stable numeric tab_id*, with name matching as fallback (names are stable: set at creation, changed only by an explicit rename).
- **`tui/`** — the ratatui/crossterm overlay (`overlay.rs`, plus `mouse.rs` helpers): lists every task across every registered workspace — sectioned by agent status (see `TaskStatus::rank`) — with fuzzy filtering, create/delete/rename/close actions, and a lean Repos view. It runs in two modes: *home* (`tenx overlay --home`, the session's long-lived base pane — jumping switches tabs without exiting, quit keys are swallowed) and *floating* (`tenx overlay`, spawned by the tenx-zellij plugin on Ctrl+w — exits after a jump and the plugin closes the pane).
- **`tenx-zellij/`** — the Ctrl+w overlay, rendered natively as a wasm zellij plugin (see its module docs for why it's a plugin, not a launcher). It's the overlay users actually see, so **any task-management feature has to land here as well as in `tui/overlay.rs`** — the two are separate implementations of the same surface and drift easily. The sandbox's filesystem is three preopened dirs — `/data` (per-plugin, persistent), `/tmp` (session-scoped, shared between plugins) and `/host` (the cwd zellij was started in) — and nothing else is reachable, so it can't walk the workspace registry or read Claude Code's session registry itself. All its data therefore arrives as one JSON document from `tenx overlay --json` (`tui::dump_json`): a `tasks` array (what to list, plus each task's current repos) and a `workspaces` array (each workspace's configured repos and whether they're cloned), which together are what the repo checklists are built from. Every mutation shells back out to a `--ws-dir` subcommand; `run_mutation_busy` keeps the overlay up on a `Mode::Busy` while one runs, because a first clone can take minutes and an error needs somewhere visible to land. Dismissing the overlay **closes** its pane (`dismiss`) rather than hiding it: a hidden instance survives reinstalls and can't be swapped from the outside, which silently pinned the session to stale code. That kills stale *panes* but is only half the staleness problem — **the zellij server also caches the compiled module, keyed by plugin path, for the life of the session**, so Ctrl+w keeps re-instantiating the wasm as it was when the server first read that path no matter how many times `make install` overwrites the file. Only `zellij action start-or-reload-plugin` evicts that cache, which is why `make install` runs it (it spawns a pane as a side effect — that's the "start" half, and esc closes it). Symptom when this goes wrong: a rebuilt overlay that looks completely unchanged, with no stale pane anywhere to explain it.
- **`tenx-statusbar/`** — the one-line bar at the bottom of every tab, a second wasm plugin. It shows this tab's task and status on the left (absorbing the old `tenx tab header` pane) and, on the right, every *other* task waiting on you, flashing a toast when one changes state while you're looking elsewhere. It **requests no permissions**, and that is the load-bearing constraint: a plugin with a pending permission request is frozen — no pipes delivered, `render` never called — and a one-row pane has nowhere to display the prompt. So it can't `run_command`, and every byte it shows arrives by pipe from `tenx watch`. Consequence to keep in mind: a bar has no way to *ask* for state, so one loading mid-session stays empty until the next change anywhere in the session. Three traps worth not rediscovering — zellij swallows a `title` key in plugin config as the pane title (hence `task_title`); column arithmetic must use the same `unicode-width` table ratatui does, because one column of overshoot wraps a one-row pane and scrolls the only line into oblivion; and the wasm is installed under a **content-addressed filename** (`tenx-statusbar-<hash>.wasm`, resolved by `zellij::statusbar_wasm`) because the zellij server caches each plugin's compiled module *keyed by path* for the life of the session — overwriting in place means a task tab opened afterwards still gets the build that was there when the session started.

  **A plugin render is never cheap, and never partial.** Before each `render` zellij wipes the pane's grid and marks the whole viewport for re-transmission (`plugin_pane.rs`: `delete_viewport_and_scroll` + `render_full_viewport`, commented as "part of the plugin contract"). So a diff against the previous frame paints onto a blanked screen — the overlay comes up almost empty — and shaving bytes in `buf_to_ansi`'s output achieves nothing either, because zellij re-encodes the pane from its own grid. **The only lever the plugin has is how often it returns `true` from `update`.** One render costs the entire pane re-sent to every attached terminal (measured: ~194 KB/s and ~200 terminal writes per second for a 194-col pane animating at 9 fps). Over ssh that is visible flicker, and at ~1 KB per write it splits a multi-byte glyph across writes tens of times a second, which any terminal that doesn't reassemble UTF-8 across reads draws as a question mark — the two symptoms look unrelated and have the same cause. Hence: the list has **no animation** (`status_icon` is static, spinner frames are reserved for `Mode::Busy`, which is transient and alone on screen), and the 1.5s data poll asks for a render only when `data_fingerprint` — the drawn form of the data, so ages hashed via `fmt_age`, not raw seconds — actually differs from what `render` last stamped. Steady state is then literally zero bytes.

## Key flows to understand together

- **No-argument invocation** (`open()` in `main.rs`): always connects to the single `tenx` session, regardless of cwd (if cwd is inside a workspace it self-heals the registry first). Inside the tenx session → runs the overlay **directly in the current pane**. Inside a *different* zellij session → switches the client in place via `zellij action switch-session` (passing `--layout` only when the session doesn't exist yet, so creation uses the home layout without appending tabs to an existing session). Outside zellij → attaches if the session exists, or creates it via `zellij --new-session-with-layout` using a layout file written to `~/.config/zellij/layouts/tenx.kdl` (required because `--layout-string`/`--layout` only append tabs to an existing session, they don't produce a clean fresh session).
- **Task creation** (`cli::task::new`): slugifies the task name (`workspace::slugify` — lowercase, spaces/underscores → dashes) for the directory/branch name but keeps the original `name` as the task's *display name*. Writes a `TASK.md` template (`# <display name>` header + Description/Todo/Links/Notes sections) and ensures the workspace-level `.claude/` exists (and is free of tenx's retired hooks), then symlinks `tasks/<slug>/.claude → ../../.claude` so Claude Code discovers workspace skills/settings from inside the task directory. For each repo in the chosen subset (`--repos`, default all): `ensure_synced` (clone-or-fetch) then `git worktree add` off the detected default branch if the task's branch doesn't already exist. Finally opens a zellij tab in the tenx session (unless `--no-open`; requires being inside that session) and records the new tab's stable `tab_id` in `tasks/<slug>/.tenx-tab-id`.
- **A task's repo set is derived from disk, never recorded**: `workspace::discover_task` builds `Task.repos` by scanning the task directory for subdirectories containing a `.git` *file* (a worktree). Nothing writes that list down, so adding or detaching a repo needs no bookkeeping — `task list`, both overlays, and `rm_in`'s cleanup loop all pick the change up for free. The verbs are `task add-repo` / `task rm-repo` (imperative) and `task set-repos` (declarative: reconcile to exactly this set, adding first so a failed clone can't leave the task half-detached). All three share `ensure_repo_worktree` with task creation, so a repo joining late gets the same treatment as one present from the start: a fresh branch named after the slug, off that repo's freshly-fetched default branch. Detaching removes the worktree *and* its task branch (same as `task rm` does per repo) and does **not** pass `--force` unless asked — git's refusal to drop a dirty worktree is the safety net, and both overlays rely on it rather than checking themselves.
- **Task display name vs. slug**: `workspace::discover_task` derives `display_name` by reading the first line of `TASK.md` (falling back to the directory name), while `name`/branch/directory all use the slug. `cli::task::open` uses the stored `.tenx-tab-id` to find the tab directly (fast path); if the TASK.md title changed since the tab was created, it renames the tab to match before switching. If the stored id is stale (tab closed, or the session was recreated), it's simply treated as not-open.
- **Claude Code integration is bidirectional**: `tenx init` optionally installs two skills into the workspace's `.claude/skills/` — `/tenx` (`src/cli/skills/tenx.md`, describing workspace layout, the boundary that a Claude session should only edit inside its own `tasks/<name>/`, and the TASK.md conventions to maintain) and `/standup` (a const string in `init.rs` describing how to run `tenx standup` and format the result into `daily.local.md`). Separately, a task's *state* (the `TaskStatus` enum in `src/workspace/mod.rs`) comes entirely from **Claude Code's own session registry**, resolved by `workspace::resolve_task_state`. **tenx installs no hooks and writes no state of its own.**

  - **Claude Code's session registry** (`src/workspace/claude.rs`) is authoritative for anything a live session can report. Claude Code writes one `~/.claude/sessions/<pid>.json` per session and rewrites it on every status change — a push-updated status file like ours, but authored by the process that actually knows. Its statuses are `busy`/`waiting`/`idle`/`shell`, and `waiting` carries a `waitingFor` reason ("input needed", the open dialog's label) that the overlay and status bar both show. Sessions are pid-checked, so a crashed one is simply gone. Background agents (`--bg`) run in a *subdirectory* of the task, so matching is by path prefix — that's also how they become visible at all (`TaskState.agents`), having been invisible to hooks that only ever read the task dir.
  - A live session that's quiet (not busy, no dialog) → `done`. Note what this is *not*: it isn't "a `Stop` hook fired". For a live session "the turn ended" and "not busy, no dialog" are the same state, and `statusUpdatedAt` already timestamps the busy→idle transition, so the age reads "waiting on you this long".
  - No live session at all → `idle`. **This is the line that carries the weight**: `done` means an agent is sitting there waiting on you, `idle` means nothing is running. An earlier cut collapsed live-but-no-`Stop`-recorded sessions into `idle`, which buried the first kind in a list of the second.

  **The hook set went six → two → one → zero, and every removal fixed a bug rather than costing a feature.**

  1. `SessionStart`/`SessionEnd`/`UserPromptSubmit`/`Notification` went first: the registry states directly what they approximated, and `Notification` approximated *worse* — `blocked` was a **latch** with no release event (approving a permission prompt fires no hook, the tool call just resumes), so a task sat atop NEEDS INPUT while Claude worked.
  2. `Stop` went next. For a live session "the turn ended" and "not busy, no dialog" are the same state, and `statusUpdatedAt` already timestamps the transition. Its only visible effect had been that `done` survived exactly **60 seconds**: `idle_prompt` (Claude Code's `messageIdleNotifThresholdMs`, 60000) fired a `Notification` right behind it and overwrote it with `blocked`. That is why the list used to read as a wall of 💬 with one lonely ✅.
  3. `StopFailure` — and with it the `failed` state — went last, deliberately trading information for simplicity: a turn that dies on an API error is the one thing the registry can't distinguish from a turn that succeeds. It now reads as `done`. Keeping it would have meant keeping `.tenx-status`, `event.sh`, `tenx tab event` and a freshness check to stop a spent failure latching forever.

  What the removals deleted, beyond the hooks themselves: the `.tenx-status` file, the `event.sh` script, the `tab event` subcommand, and the overlay's entire staleness apparatus (`drop_stale_dead_statuses`, `STALE_AFTER`, `LIVENESS_TTL`, the cached zellij tab query) — liveness had been inferred from whether the *zellij tab* still existed, after a 3-minute grace period, where a pid either exists or it doesn't. `tenx hooks install` keeps its name because that's what an upgrading user knows to run, but it now *removes* tenx's hook entries from `.claude/settings.json` (leaving foreign hooks alone), deletes our scripts, and clears leftover `.tenx-status` files. The overlay renders each state with its own glyph (💬 blocked / ✅ done / ▷ working; tab names are never touched) and, by default, *groups the task list* into `TaskGroup` sections — WAITING FOR INPUT, WORKING, INACTIVE — with `TaskStatus::rank` ordering within each and recency as the final tiebreak. Sections are deliberately coarser than statuses: `blocked` and `done` share the first one, because two adjacent headers both meaning "waiting on you" helped nobody, and the row's glyph plus Claude's waiting reason carry the difference while blocked floats to the top. Both overlays freeze a row's section at open (`Row.group`; the plugin's `order` snapshot, which stores the *status* rank since the section derives from it) and only refresh the glyph on the tick, so a status change mid-view can't tear a section in two or slide rows out from under the cursor; the plugin's → cycles status → recent → workspace.
- **The attention watcher** (`cli::watch`): a detached background process that notifies you when a task starts waiting on you — the one thing the overlay can't do, because it only knows a state while you're looking at it. `main::open()` is the single funnel for every route into the session (attach, create, switch-session), so `ensure_running` hangs off it: start the session, get a watcher. Single-instance via `~/.config/tenx/watch.pid` + the same pid-liveness test the registry gets read with, guarded in *both* `ensure_running` and `run` (`tenx watch` is a command someone can run twice, and two watchers means two notifications for one prompt). It exits once the zellij session is gone, so it can't outlive what it watches.

  It notifies on the **edge into `blocked`**, not on every state: `done` fires after every single turn and would be constant noise. Tasks already waiting when it starts are primed as "already notified" — a backlog of prompts is not attention, it's a burst of noise on login. It won't re-notify while a task stays blocked, and re-arms once the prompt is answered. Delivery is `terminal-notifier` when installed, `osascript` otherwise (always present on macOS, so there is no path where the watcher runs but can't speak); task titles come from `TASK.md`, i.e. arbitrary user text, so the AppleScript string is escaped.

  **Why a process and not a zellij plugin**: measured, `zellij pipe --plugin <url>` launches a plugin *with a pane* (session pane count 11 → 13, `plugin location=` in the layout dump) and `zellij plugin` says as much in its help — zellij 0.44 has no paneless plugin. A watcher needing a visible pane recreates the leftover-pane problems the tabless design exists to avoid. A process also serves every consumer; a plugin can only pipe to other plugins. It polls (~5 ms per resolve) rather than using `watch_filesystem`, which zellij's own docs call "somewhat unstable".

- **`tenx standup`** (`cli::standup`): reads every task's `TASK.md` verbatim (authoritative source for PR/Linear links) plus parses `~/.claude/projects/<slug>*/*.jsonl` Claude Code session logs — filtering to user messages and `git commit`/`git push` bash tool calls since the last standup (tracked via a `<!-- last-standup: ... -->`-adjacent heading in the workspace's `daily.local.md`, or defaulting to the start of yesterday). Project slugs are matched by replacing `$HOME` and `/` with `-` in the workspace path, so any Claude Code project whose path is under this workspace is picked up. This raw output is meant to be fed to the `/standup` skill, not read directly by users.
