# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tenx` is a CLI + TUI tool (Rust) that manages multi-repo "workspaces" and "tasks". A workspace holds one or more bare git repos; a task is a named unit of work that creates a git worktree (on a branch matching the task's slug) in each of the workspace's repos, then opens a claude/nvim/shell window for that task inside the single global **tmux** session. It also drives a Claude Code integration layer of its own (skills, plus live task state read from Claude Code's session registry) and a `standup` command that summarizes recent Claude Code activity — so this tool is itself part of the harness a Claude Code session runs inside when working in a `tenx`-managed task.

This is the **v2 rebuild** (v1 ran on zellij with two wasm plugins; `ARCHITECTURE.md` is the human-oriented map of the current design, `README.md` the user-facing one). The reasons for the switch, in one line each: tmux control mode and headless attach make a client outside tmux possible; tmux control mode is the proven protocol for a future native client; `monitor-bell` gives a generic attention channel; headless tmux makes end-to-end tests possible.

## Commands

```sh
cargo build --release          # build
cargo run -- <args>            # e.g. `cargo run -- task list`
make test                      # cargo test + clippy -D warnings, both crates
make install                   # cargo install --path . (nothing else to place)
make release auto              # version + CHANGELOG from commits (git-cliff); never pick a version or write changelog text by hand. Or: gh workflow run bump.yml
make screenshot                # re-render docs/column.svg from fixtures (src/tui/column/screenshot.rs)
make demo                      # re-render docs/demo.svg + .cast from a scripted client session (src/tui/column/demo.rs)
make demo-gif                  # docs/demo.gif from the cast via agg; scripts/release.sh runs both at release time
tenx internal tmux-conf        # print the generated tmux config (hidden command)
```

CI (`.github/workflows/ci.yml`) runs build/test/clippy on macOS and Ubuntu. `Cargo.lock` is checked in. The package is `tenx-cli` (crates.io `tenx` is taken); the binary is `tenx`, so `cargo test -p tenx-cli --bin tenx`. `.github/workflows/release.yml` is generated by cargo-dist from `dist-workspace.toml` — never edit it by hand, run `dist generate`. It runs on `workflow_dispatch` only and creates the tag itself; nothing else tags. **Commit messages are the changelog**: Conventional Commits, area as scope — `feat(column): …`, `fix(tmux): …`, `refactor(secrets): …`, `docs: …`, `chore:`/`ci:`/`test:` (those three are left out of the changelog). Subject line in the imperative, user-facing wording: it is printed verbatim in CHANGELOG.md and the release notes (`cliff.toml`). `feat` bumps minor, `fix` patch; mark breaking changes with `!`. Never edit CHANGELOG.md by hand. `make hooks` once per clone installs the `commit-msg` hook that rejects other formats (`scripts/check-commit-msg.sh`); CI checks every pushed commit the same way. CI secrets live encrypted in `secrets/ci.enc.env` (sops + age, recipients in `.sops.yaml`: maintainer + CI identity); the custom publish job `publish-homebrew.yml` decrypts them in CI with the one GitHub secret `SOPS_AGE_KEY`. Never decrypt them to stdout — `tenx secrets decrypt ci.enc.env` releases them agent-safely to a gitignored sibling.

## Crates

- **`tenx-core/`** — pure logic, no `Command`, no filesystem beyond what a caller hands in: `status` (`TaskStatus`/`TaskGroup`/`TaskState`, `Session`, `resolve_task_state`), `dialog` (answering a permission prompt: `Answer`, `permission_dialog_visible`, `pane_id`, `preview_tail`), `slug` (`slugify`), `time` (`format_age`, `parse_duration`), `sweep` (`sweep_reason`, `DEFAULT_SWEEP_AFTER`), `taskmd` (`render_task_md`, `display_name`, `with_title`), `column` (`width`: the task column's size rule). **Unit tests live here** — put any new decision logic here first, then call it from the binary. `workspace::` re-exports the status types so call sites keep their paths.
- **`tenx`** (root) — the binary: CLI, client, watcher.

## Architecture (binary)

Independent layers wired together by `main.rs`'s CLI dispatch; each layer only knows about the layer(s) below it:

- **`cli/`** — clap-based argument parsing (`mod.rs`) plus one file per subcommand group: `init.rs`, `repo.rs`, `task.rs`, `standup.rs`, `hooks.rs`, `watch.rs`, `secrets.rs`, `notify.rs`. The column calls directly into these functions (`cli::task::{new_in,open_in,rm_in,set_repos_in}`, `cli::repo::add_in`, `cli::secrets::fulfill_in`) instead of duplicating logic. Every mutating command also takes `--ws-dir` for scripts/front ends that don't run inside the workspace. A hidden `internal` group holds plumbing (`tmux-conf`, `ports`, `agent-log`).
- **`workspace/`** — the on-disk model. A *workspace* is a directory with a `config.toml` (name, layout script path, list of repos, optional `age_identity`) and a `tasks/` subdirectory; each subdirectory under `tasks/` is a *task*. `workspace::find()` walks up from cwd looking for `config.toml`. Global user config lives at `~/.config/tenx/config.toml` (`bare_dir` override; `column_width`, 0 = automatic). The workspace *registry* is one file per workspace under `~/.config/tenx/workspaces.d/<name>-<pathhash>.toml` — registration is a single atomic file write; pruning is a per-file delete. Config writes are atomic (write to `.toml.tmp`, then rename). `workspace/claude.rs` reads Claude Code's session registry (filesystem + pid checks); what a session list *means* is `tenx_core::status`.
- **`git/`** — shells out to the system `git` for everything (bare clone, fetch, worktree add/remove, default-branch detection) so SSH agent / credential helpers behave like the user's own `git`. Bare repos live under `<workspace>/.bare/<name>.git` by default. `ensure_synced()` clones or fetches — the entry point task creation uses.
- **`progress.rs`** — a threaded spinner for clone/fetch/worktree operations.
- **`live.rs`** — the per-task `.tenx-live.json` cache of external facts: listening ports (window pane pids → `ps` descendants → `lsof` listeners) and PRs (`gh pr view --json`). Only `tenx watch` writes it (`refresh_live`: ports every tick; PRs staggered, on a helper thread, 2 min TTL active / 30 min parked, ≤2 lookups per tick); the column, `task_json` and the status line only read it. Parsing and chip text are `tenx_core::live`. `tenx internal ports` prints the current port map.
- **`tmux/`** — the session layer. tenx runs its **own tmux server** on a dedicated socket (`tmux -L tenx`, `TENX_TMUX_SOCKET` overrides for tests), started against a generated `~/.config/tenx/tmux.conf` (`render_config`: theme from `palette.rs`, blanked window list, `status-left` from the `@tenx_status` window option, `status-right` from the global `@tenx_right`, `monitor-bell on`; no key bindings — the column is outside tmux). The user's `~/.tmux.conf` is untouched. **Windows are tasks**, named by slug (immutable, unique within a workspace) and tracked by their stable `@id`, cached per task in `.tenx-window-id` as a fast path only — `find_window` by name is the truth. `open_task_window` builds the default layout (claude left; nvim on `TASK.md` top-right; shell bottom-right) with `new-window`/`split-window`, or runs the workspace's `layout` script with `TENX_WINDOW`/`TENX_SLUG`/`TENX_TASK_DIR`/`TENX_WS_DIR`/`TENX_CLAUDE_CMD`/`TENX_TMUX` in the environment. `ensure_session` starts the server detached with window 0 (`home`) as a plain shell in `$HOME`, never a task window; `attach_command` is the `tmux attach` the client runs in its pty; `current_task` names the session's current window. tmux reads the config only at server start — after changing `render_config`, `tmux -L tenx kill-server` then `tenx`.
- **`tui/client.rs` + `tui/term.rs`** — what `tenx` opens (`main::open`, anywhere but inside the tenx session): one process owning the terminal, the column (`tui/column.rs`) on the left, and `tmux attach` running in a pty on the right (`term::EmbeddedTerminal`: portable-pty + a `vt100` parser painted by `tui-term`'s widget; the reader thread scans raw output for BEL and OSC 52, which the client forwards to the real terminal; `encode_key`/`encode_mouse` turn crossterm events back into bytes, honouring DECCKM and SGR mouse; paste is bracketed when the program asked for it). `Ctrl+w` never reaches tmux: it cycles show+focus (cursor on the current task, `select_current`) / hide (`Client::cycle`); the column asks for focus changes through `ClientRequest` (a jump or quit key → `FocusTerminal`, `:hide`, `:q` → `Quit`), and the column drops its highlight whenever the keyboard leaves it (`blur`). A closed task under the cursor is drawn as an empty "⏎ open it here" screen in the task area. A status change re-groups the column at once (`tidy`, selection kept by slug). Only a click moves focus; the wheel scrolls the view. The inner tmux runs with `TMUX` unset (nesting guard), `tmux::ensure_session` starts the server detached if needed, and the client starts on a task window rather than the home shell when one exists. Terminals under 100 columns hide the column and show the list full screen. `TENX_CLIENT_LOG=<file>` traces every key and mouse event with the column's state. The emulator is the one swappable part (alacritty_terminal or wezterm-term if vt100's fidelity bites).
- **`tui/column.rs`** — the task list (`Column`), drawn by the client as its left-hand strip (`render_in`). Lists every task across every registered workspace, sectioned by `TaskGroup` (secrets pending → waiting for input → working → inactive), fuzzy-filtered, two lines per task (`column_items`: title, then reason/workspace/age/chips as far as they fit; closed tasks dimmer, the current task's title in the "current" colour), with Telescope-style modes (search field = Insert; list row = Normal: `n` new, `a` add repo, `r` rename, `e` edit repos, `x` close window, `u` unlock secrets, `y`/`N` approve/deny a permission prompt, `dd` delete, `Enter`/`o`/`l` open, `:` commands incl. `:cancel`, `:hide`, `:q`). ↓/↑ from the search field enter the list next to the current task (`own_row`); `follow_selection` switches windows as the selection moves onto a task with an open window; a jump (`open_in`) keeps the rows and the selection and asks the client for focus (`ClientRequest`). Rows are rebuilt (`rebuild_rows`, re-sorted, selection kept by slug via `tidy`) when a status moves a task to another section, when task directories appear or vanish (`task_dir_count` on the slow refresh), or after create/delete/rename/close; between rebuilds the idle tick updates status, age and window in place (`refresh_statuses`; `list-windows` every 2 s feeds both the bell signals and the open-window set, never the per-task cache file). `y`/`N` (`Column::answer`) re-read the registry and re-capture the pane right before `send-keys Enter`/`Escape`, and refuse unless the session is waiting on a *permission prompt* and `tenx_core::dialog::permission_dialog_visible` sees the dialog — see that module's doc for why keystrokes are the only channel. `Column::empty` builds one with no I/O; `column/screenshot.rs` (test-only) fills it with fixture rows, renders through ratatui's `TestBackend`, asserts every section and chip kind appears, and with `TENX_SCREENSHOT` set writes `docs/column.svg`. `column/demo.rs` (test-only) plays a scripted client session — keystrokes through the real handlers, a fixture task screen on the right, one row flipped to `Blocked` — and with `TENX_DEMO` writes every frame as an animated SVG and an asciinema cast. The README images are generated from the real widgets, never from a real workspace.

## Key flows to understand together

- **No-argument invocation** (`open()` in `main.rs`): self-heals the registry if cwd is in a workspace, checks `tmux -V ≥ 3.3`, ensures the watcher, then: inside the tenx session → only a hint (the column is on the left); anywhere else (a plain terminal, or a pane of some other tmux — the client's inner tmux runs with `TMUX` unset, so nesting is fine) → the client (`tui::client::run`), which starts the server if needed. Over SSH, `tenx` does the same thing — same server, same session, a column of its own.
- **Task creation** (`cli::task::new_in`): slugifies the name (`tenx_core::slug::slugify` — lowercase, `[a-z0-9]` only, runs collapsed to `-`; an empty slug is an error) for the directory/branch/window name but keeps the original as the display name. Writes `TASK.md` from `tenx_core::taskmd::render_task_md`, retires any old tenx hooks in the workspace's `.claude/`, symlinks `tasks/<slug>/.claude → ../../.claude`, then per repo: `ensure_synced` + `git worktree add -B <slug>` off the freshly-fetched default branch. Then (unless `--no-open`, and only if the server is running) opens the window and records its id.
- **A task's repo set is derived from disk, never recorded**: `discover_task` scans for subdirectories containing a `.git` *file*. `task add-repo`/`rm-repo` (imperative) and `task set-repos` (declarative, adds before removes) share `ensure_repo_worktree` with creation. Detaching removes the worktree *and* its branch and does not `--force` unless asked — git's refusal to drop a dirty worktree is the safety net.
- **Task display name vs. slug**: `display_name` is `TASK.md`'s first heading (fallback: directory name); slug/branch/directory/window all use the slug. `task rename` rewrites only the heading.
- **Task names typed by a human** (`task open/rm/pin/…` without `--ws-dir`) resolve via `cli::task::slug_for`: the exact directory name if such a task exists (tasks created before `slugify` tightened may have punctuation in their names), else the slugified name. `task new` also refuses a title that matches an existing task's display name, and the slug `home` (the session's shell window).
- **Task open** (`open_in`): `find_window(slug)` → `select-window` (this changes the *session's* current window, so it works from any client and from outside one); else create the window, passing `--continue` to claude only if `has_claude_conversation` finds a transcript for that exact directory (otherwise claude exits 1 and the pane vanishes).
- **Sweep / pin** (`cli::task::sweep_candidates` + `tenx_core::sweep::sweep_reason`): closes windows nobody is waiting on — never the current window, a pinned task (`.tenx-pinned`), or a `Blocked`/`Working` task; `Idle` immediately, `Done` after `--after` (default 8h). Reopening recreates the window and `--continue` picks the conversation back up.
- **Claude Code integration is bidirectional**: `tenx init` optionally installs `/tenx` (`src/cli/skills/tenx.md`) and `/standup` skills into `.claude/skills/`. A task's *state* comes from **Claude Code's session registry** (`~/.claude/sessions/<pid>.json`, pid-checked **and scoped to sessions whose pid descends from a pane of the tenx tmux server** — `tenx_core::status::in_panes`; the registry is per user, so a Claude in a plain terminal or an abandoned multiplexer would otherwise pin its task's status; the one exception is a *parked turn*'s worker — `claude bg-spare` under the Claude daemon, off `init`, `kind` "bg", `jobId` matching an in-pane interactive session's `parkedJobId` — which is the entry that says `waiting` while the permission dialog is drawn in the interactive pane, and the interactive entry's own status is frozen from the moment it parked; `in_panes` keeps the worker and `fold_parked` merges the pair into the interactive session with the worker's status, so a parked turn is one session, never an agent) merged with its **tmux window's bell flag** (`tmux::signals()`, keyed by slug): any `waiting` → `Blocked` (with Claude's reason), else a bell → `Signaled` (🔔 — any process in any pane can `printf '\a'`; tmux clears it when the window is visited), else any `busy` → `Working`, else a quiet live session → `Done`, none → `Idle`. `Blocked` and `Signaled` are the "needs you" states (`TaskStatus::needs_you`): the watcher notifies on their edge and `sweep` never closes them. **tenx installs no hooks and writes no state of its own**; `tenx hooks install` *removes* the retired v0 hooks. Background agents (`--bg`) run in a subdirectory and are matched by path prefix. The `failed` state was dropped deliberately: the registry can't tell a failed turn from a finished one.
- **The attention watcher** (`cli::watch`): a detached, single-instance process (`~/.config/tenx/watch.pid`; liveness via `pid_alive`, which counts a zombie as dead) started by `open()` with a double fork so init reaps it — its parent must never be the long-lived client, or a killed watcher lingers as a zombie that keeps "already running" true, polling every 2 s (~5 ms per resolve). Two consumers, one resolve pass: a desktop notification on the *edge* into `Blocked` (debounced; tasks already waiting at start are primed as notified; `Done` never notifies — it fires after every turn), delivered via `cli::notify::platform()` (macOS: `terminal-notifier`/`osascript`; Linux: `notify-send`; the mark from `docs/logo/tenx-mark-256.png` is embedded and written to `~/.config/tenx/tenx.png` as the icon, `cli::notify::icon_path`); and `push_status`, which sets `@tenx_status` on each open task window (glyph from `TaskStatus::glyph`, 🔒 when secrets are pending, the bold title, the workspace name muted, then the row's PR/port chips) and the global `@tenx_right` — counting only tasks *other than the current window's*, with `Done` gated on 60 s unanswered so the corner doesn't flicker with every turn you type — only when the digest or the live cache changes, so a quiet session sends nothing. Secrets-pending queues are tracked as further independent edges. It also gives every background agent (`--bg`, a non-interactive session under a task) a 12-line pane in its task's window, once per (cwd, pid), running `tenx internal agent-log` (`cli::agentlog`) — a compact follower of the agent's transcript that exits with the agent. Exits once the tmux server is gone.
- **`tenx secrets`** (`cli::secrets`): task-scoped credentials via the system `age`/`sops`. Read that module's doc comment before touching it — the invariants (never print a value to stdout; `/dev/tty` reachability decides whether `decrypt`/`set` act or enqueue-and-wait; adopted secrets decrypt outside the worktree and are symlinked in) are the whole design. The no-terminal wait (`wait_for_human`, bounded by `--timeout`, default `DEFAULT_WAIT` = 100 s so a shell tool's 2 min kill never hits first; `--no-wait` to skip) polls the queue and decides fulfilled-vs-withdrawn from output mtimes via `tenx_core::secrets::wait_outcome` — no receipt files. `cancel <name>|--all` (CLI, and `:cancel` in the column) only edits the queues.
- **`tenx standup`** (`cli::standup`): prints every `TASK.md` plus user prompts and `git commit`/`git push` calls from `~/.claude/projects/<slug>*/*.jsonl` since the last standup (first `## ` heading in `daily.local.md`, else start of yesterday). Meant to be fed to the `/standup` skill.

## Conventions

- Decision logic goes in `tenx-core` with a test; the binary does I/O.
- Derive state from live sources (disk, the session registry, `tmux list-windows`) rather than recording it; the only tenx-owned per-task files are `.tenx-window-id` (a cache — never act destructively on it, look the window up by slug), `.tenx-pinned`, `.tenx-live.json` (a cache of external facts, written only by the watcher), and the two secrets-pending queues.
- Shell out to the real `git`/`tmux`/`age`/`sops`; never link a library for them.
- Keep `make test` green: clippy runs with `-D warnings`.
