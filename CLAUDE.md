# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tenx` is a CLI + TUI tool (Rust) that manages multi-repo "workspaces" and "tasks". A workspace holds one or more bare git repos; a task is a named unit of work that creates a git worktree (on a branch matching the task's slug) in each of the workspace's repos, then opens a claude/nvim/shell window for that task inside the single global **tmux** session. It also drives a Claude Code integration layer of its own (skills, plus live task state read from Claude Code's session registry) and a `standup` command that summarizes recent Claude Code activity — so this tool is itself part of the harness a Claude Code session runs inside when working in a `tenx`-managed task.

This is the **v2 rebuild** (v1 ran on zellij with two wasm plugins; `ARCHITECTURE.md` is the human-oriented map of the current design, `README.md` the user-facing one). The reasons for the switch, in one line each: tmux `display-popup` is per-client so one ratatui overlay serves every surface; tmux control mode is the proven protocol for a future native client; `monitor-bell` gives a generic attention channel; headless tmux makes end-to-end tests possible.

## Commands

```sh
cargo build --release          # build
cargo run -- <args>            # e.g. `cargo run -- task list`
make test                      # cargo test + clippy -D warnings, both crates
make install                   # cargo install --path . (nothing else to place)
make release auto              # version + CHANGELOG from commits (git-cliff); never pick a version or write changelog text by hand. Or: gh workflow run bump.yml
make screenshot                # re-render docs/overlay.svg from fixtures (src/tui/overlay/screenshot.rs)
make demo                      # re-render docs/overlay-demo.svg + .cast from a scripted scene (src/tui/overlay/demo.rs)
make demo-gif                  # docs/overlay-demo.gif from the cast via agg; scripts/release.sh runs both at release time
tenx internal tmux-conf        # print the generated tmux config (hidden command)
```

CI (`.github/workflows/ci.yml`) runs build/test/clippy on macOS and Ubuntu. `Cargo.lock` is checked in. The package is `tenx-cli` (crates.io `tenx` is taken); the binary is `tenx`, so `cargo test -p tenx-cli --bin tenx`. `.github/workflows/release.yml` is generated by cargo-dist from `dist-workspace.toml` — never edit it by hand, run `dist generate`. It runs on `workflow_dispatch` only and creates the tag itself; nothing else tags. **Commit messages are the changelog**: Conventional Commits, area as scope — `feat(overlay): …`, `fix(tmux): …`, `refactor(secrets): …`, `docs: …`, `chore:`/`ci:`/`test:` (those three are left out of the changelog). Subject line in the imperative, user-facing wording: it is printed verbatim in CHANGELOG.md and the release notes (`cliff.toml`). `feat` bumps minor, `fix` patch; mark breaking changes with `!`. Never edit CHANGELOG.md by hand. `make hooks` once per clone installs the `commit-msg` hook that rejects other formats (`scripts/check-commit-msg.sh`); CI checks every pushed commit the same way. CI secrets live encrypted in `secrets/ci.enc.env` (sops + age, recipients in `.sops.yaml`: maintainer + CI identity); the custom publish job `publish-homebrew.yml` decrypts them in CI with the one GitHub secret `SOPS_AGE_KEY`. Never decrypt them to stdout — `tenx secrets decrypt ci.enc.env` releases them agent-safely to a gitignored sibling.

## Crates

- **`tenx-core/`** — pure logic, no `Command`, no filesystem beyond what a caller hands in: `status` (`TaskStatus`/`TaskGroup`/`TaskState`, `Session`, `resolve_task_state`), `dialog` (answering a permission prompt: `Answer`, `permission_dialog_visible`, `pane_id`, `preview_tail`), `slug` (`slugify`), `time` (`format_age`, `parse_duration`), `sweep` (`sweep_reason`, `DEFAULT_SWEEP_AFTER`), `taskmd` (`render_task_md`, `display_name`, `with_title`), `snapshot` (the watcher→sidebar document: `Snapshot`/`TaskSnap`, `is_fresh`), `sidebar` (`width`: the column's size rule). **Unit tests live here** — put any new decision logic here first, then call it from the binary. `workspace::` re-exports the status types so call sites keep their paths.
- **`tenx`** (root) — the binary: CLI, overlay, watcher.

## Architecture (binary)

Independent layers wired together by `main.rs`'s CLI dispatch; each layer only knows about the layer(s) below it:

- **`cli/`** — clap-based argument parsing (`mod.rs`) plus one file per subcommand group: `init.rs`, `repo.rs`, `task.rs`, `standup.rs`, `hooks.rs`, `watch.rs`, `secrets.rs`, `notify.rs`. The overlay calls directly into these functions (`cli::task::{new_in,open_in,rm_in,set_repos_in}`, `cli::repo::add_in`, `cli::secrets::fulfill_in`) instead of duplicating logic. Every mutating command also takes `--ws-dir` for scripts/front ends that don't run inside the workspace. A hidden `internal` group holds plumbing (`tmux-conf`, `ports`, `agent-log`, and `sidebar cycle|toggle` — `cli/sidebar.rs`; `cycle` is what the Ctrl+w binding runs).
- **`workspace/`** — the on-disk model. A *workspace* is a directory with a `config.toml` (name, layout script path, list of repos, optional `age_identity`) and a `tasks/` subdirectory; each subdirectory under `tasks/` is a *task*. `workspace::find()` walks up from cwd looking for `config.toml`. Global user config lives at `~/.config/tenx/config.toml` (`bare_dir` override; `sidebar = true|false`, default false — the pane sidebar is the pre-client layout; `sidebar_width`, 0 = automatic). The workspace *registry* is one file per workspace under `~/.config/tenx/workspaces.d/<name>-<pathhash>.toml` — registration is a single atomic file write; pruning is a per-file delete. Config writes are atomic (write to `.toml.tmp`, then rename). `workspace/claude.rs` reads Claude Code's session registry (filesystem + pid checks); what a session list *means* is `tenx_core::status`.
- **`git/`** — shells out to the system `git` for everything (bare clone, fetch, worktree add/remove, default-branch detection) so SSH agent / credential helpers behave like the user's own `git`. Bare repos live under `<workspace>/.bare/<name>.git` by default. `ensure_synced()` clones or fetches — the entry point task creation uses.
- **`progress.rs`** — a threaded spinner for clone/fetch/worktree operations.
- **`snapshot.rs`** — I/O for the watcher's sidebar snapshot, `~/.config/tenx/sidebar.json` (socket-suffixed like the tmux config): every task with status, timestamps, window, pane and chips (`tenx_core::snapshot`). `publish` writes atomically only when the document changed and otherwise touches the mtime, so a reader polls one `stat` per tick and the mtime is the watcher's liveness signal (`modified_fresh`/`read_fresh` return nothing after 10 s without a touch).
- **`live.rs`** — the per-task `.tenx-live.json` cache of external facts: listening ports (window pane pids → `ps` descendants → `lsof` listeners) and PRs (`gh pr view --json`). Only `tenx watch` writes it (`refresh_live`: ports every tick; PRs staggered, on a helper thread, 2 min TTL active / 30 min parked, ≤2 lookups per tick); the overlay, `task_json` and the status line only read it. Parsing and chip text are `tenx_core::live`. `tenx internal ports` prints the current port map.
- **`tmux/`** — the session layer. tenx runs its **own tmux server** on a dedicated socket (`tmux -L tenx`, `TENX_TMUX_SOCKET` overrides for tests), started against a generated `~/.config/tenx/tmux.conf` (`render_config`: theme from `palette.rs`, blanked window list, `status-left` from the `@tenx_status` window option, `status-right` from the global `@tenx_right`, `monitor-bell on`, `bind -n C-w if-shell -F <client smaller than 100×30> {display-popup -E -B -w 100% -h 100% … tenx overlay} {if-shell -F "#{==:#{window_name},home}" {} {run-shell -b "tenx internal sidebar cycle '#{pane_id}'"}}` — full screen on a phone; in a task window `cli::sidebar::cycle`: from the task, show the sidebar (opening one if hidden) and focus it, from inside it hide it; nothing in the home window, which is the list). The user's `~/.tmux.conf` is untouched. **The sidebar pane**: with `sidebar = true` (and no `tenx client` running — it sets the global option `@tenx_client` while it draws the column outside tmux, and `cli::sidebar::wanted` then says no) `open_task_window` finishes by splitting a full-height pane (`split-window -hbfd`, `open_sidebar`) on the left of the task running `tenx overlay --sidebar` in a restart loop, 20% of the window clamped to 30–48 columns (`tenx_core::sidebar::width`, or `sidebar_width`), marked with the pane option `@tenx_sidebar`. tmux numbers panes by position, so the sidebar is pane 0 and the task starts at 1 — `main_pane` (lowest non-sidebar index) is where a jump lands and where `open_agent_pane` splits from; never assume `.0` is Claude. **Windows are tasks**, named by slug (immutable, unique within a workspace) and tracked by their stable `@id`, cached per task in `.tenx-window-id` as a fast path only — `find_window` by name is the truth. `open_task_window` builds the default layout (claude left; nvim on `TASK.md` top-right; shell bottom-right) with `new-window`/`split-window`, or runs the workspace's `layout` script with `TENX_WINDOW`/`TENX_SLUG`/`TENX_TASK_DIR`/`TENX_WS_DIR`/`TENX_CLAUDE_CMD`/`TENX_TMUX` in the environment. `attach_or_create` execs `new-session -A` with the home window running `tenx overlay --home` in a restart loop. tmux reads the config only at server start — after changing `render_config`, `tmux -L tenx kill-server` then `tenx`.
- **`tui/client.rs` + `tui/term.rs`** (experimental, `tenx client`) — the per-terminal client: one process owning the terminal, the overlay on `Surface::Client` as a column on the left, and `tmux attach` running in a pty on the right (`term::EmbeddedTerminal`: portable-pty + a `vt100` parser painted by `tui-term`'s widget; the reader thread scans raw output for BEL and OSC 52, which the client forwards to the real terminal; `encode_key`/`encode_mouse` turn crossterm events back into bytes, honouring DECCKM and SGR mouse; paste is bracketed when the program asked for it). `Ctrl+w` never reaches tmux: it cycles show+focus / hide (`Client::cycle`); the overlay asks for focus changes through `ClientRequest` (a jump or quit key → `FocusTerminal`, `:hide`, `:q` → `Quit`). The inner tmux runs with `TMUX` unset (nesting guard), `tmux::ensure_session` starts the server detached if needed, and the client starts on a task window rather than home so the list isn't shown twice. Narrow terminals hide the column and show the list full screen. The emulator is the one swappable part (alacritty_terminal or wezterm-term if vt100's fidelity bites).
- **`tui/`** — the ratatui overlay (`overlay.rs`, plus `mouse.rs`). **The only overlay implementation.** Lists every task across every registered workspace, sectioned by `TaskGroup` (secrets pending → waiting for input → working → inactive), fuzzy-filtered, with Telescope-style modes (search field = Insert; list row = Normal: `n` new, `a` add repo, `r` rename, `e` edit repos, `x` close window, `u` unlock secrets, `y`/`N` approve/deny a permission prompt, `dd` delete, `Enter`/`o`/`l` jump, `:` commands incl. `:cancel` to withdraw secrets requests). A **preview panel** (beside the list from 96 columns; narrower, under it from 26 rows and only while the selected task is `Blocked`, so a phone keeps the full list otherwise; else absent) shows the selected task's Claude pane via `tmux capture-pane -e`, rendered through `tui/ansi.rs`, refreshed on selection change and every tick — the pane comes from the registry's own `tmux` field (`Session.pane`). `y`/`N` (`Overlay::answer`) re-read the registry and re-capture the pane right before `send-keys Enter`/`Escape`, and refuse unless the session is waiting on a *permission prompt* and `tenx_core::dialog::permission_dialog_visible` sees the dialog — see that module's doc for why keystrokes are the only channel. Three surfaces (`tui::Surface`): *home* (`--home`, the session's permanent window 0 — jump selects the task's window and stays; quit keys are swallowed), *popup* (`tenx overlay` under `display-popup -E` — exits after a jump, tmux closes the popup) and *sidebar* (`--sidebar`, one per task window: rows come from the watcher's snapshot while its mtime is fresh — `refresh_from_snapshot`, in place when the task set is unchanged — and from live resolution otherwise, with a "no watcher" footer; no preview panel; the title takes the row and the workspace only leftover space; the current task's title is drawn in the "current" colour; the search field is the resting state as everywhere, but ↓/↑ from it enter the list next to the window's own task (`own_row`) rather than at the top, and `follow_selection` switches windows as j/k/arrows/clicks move it onto a task with an open window, then focuses that window's sidebar (`cli::sidebar::ensure_focused`) — the wheel only browses; a jump `select-window`s then `select-pane`s the target's `main_pane`; quit keys hand focus back to the task and leave the column; Ctrl+w from inside hides it; `:hide` removes the pane and `:sidebar` toggles one in the current window from any surface). Run from a plain terminal outside tmux, a jump records an `AttachTarget` and `run()` attaches after teardown. The home instance runs a rate-limited background sweep on focus-gained. `Overlay::empty` builds one with no I/O; `overlay/screenshot.rs` (test-only) fills it with fixture rows, renders through ratatui's `TestBackend`, asserts every section and chip kind appears, and with `TENX_SCREENSHOT` set writes the buffer as `docs/overlay.svg` (and the 36-column sidebar render as `docs/sidebar.svg`) — the README images are generated from the real widgets, never from a real workspace. `overlay/demo.rs` (test-only) goes further: it plays a scripted scene — keystrokes through `handle_key`, plus one fixture row flipped to `Blocked` — and with `TENX_DEMO` writes every frame as an animated SVG (stepped CSS keyframes, one `<g>` per frame) and an asciinema v2 cast.

## Key flows to understand together

- **No-argument invocation** (`open()` in `main.rs`): self-heals the registry if cwd is in a workspace, checks `tmux -V ≥ 3.3` (the generated config uses `display-popup -T` and popup styling), ensures the watcher, then: inside the tenx session → run the overlay in this pane; inside some *other* tmux server → error with `tmux::foreign_client_hint()` (no cross-server switch exists; nesting is a trap); outside tmux → `attach_or_create` (exec). Over SSH, `tenx` does the same thing — same server, same session.
- **Task creation** (`cli::task::new_in`): slugifies the name (`tenx_core::slug::slugify` — lowercase, `[a-z0-9]` only, runs collapsed to `-`; an empty slug is an error) for the directory/branch/window name but keeps the original as the display name. Writes `TASK.md` from `tenx_core::taskmd::render_task_md`, retires any old tenx hooks in the workspace's `.claude/`, symlinks `tasks/<slug>/.claude → ../../.claude`, then per repo: `ensure_synced` + `git worktree add -B <slug>` off the freshly-fetched default branch. Then (unless `--no-open`, and only if the server is running) opens the window and records its id.
- **A task's repo set is derived from disk, never recorded**: `discover_task` scans for subdirectories containing a `.git` *file*. `task add-repo`/`rm-repo` (imperative) and `task set-repos` (declarative, adds before removes) share `ensure_repo_worktree` with creation. Detaching removes the worktree *and* its branch and does not `--force` unless asked — git's refusal to drop a dirty worktree is the safety net.
- **Task display name vs. slug**: `display_name` is `TASK.md`'s first heading (fallback: directory name); slug/branch/directory/window all use the slug. `task rename` rewrites only the heading.
- **Task names typed by a human** (`task open/rm/pin/…` without `--ws-dir`) resolve via `cli::task::slug_for`: the exact directory name if such a task exists (tasks created before `slugify` tightened may have punctuation in their names), else the slugified name. `task new` also refuses a title that matches an existing task's display name, and the slug `home` (the overlay's window).
- **Task open** (`open_in`): `find_window(slug)` → `select-window` (this changes the *session's* current window, so it works from any client and from outside one); else create the window, passing `--continue` to claude only if `has_claude_conversation` finds a transcript for that exact directory (otherwise claude exits 1 and the pane vanishes).
- **Sweep / pin** (`cli::task::sweep_candidates` + `tenx_core::sweep::sweep_reason`): closes windows nobody is waiting on — never the current window, a pinned task (`.tenx-pinned`), or a `Blocked`/`Working` task; `Idle` immediately, `Done` after `--after` (default 8h). Reopening recreates the window and `--continue` picks the conversation back up.
- **Claude Code integration is bidirectional**: `tenx init` optionally installs `/tenx` (`src/cli/skills/tenx.md`) and `/standup` skills into `.claude/skills/`. A task's *state* comes from **Claude Code's session registry** (`~/.claude/sessions/<pid>.json`, pid-checked **and scoped to sessions whose pid descends from a pane of the tenx tmux server** — `tenx_core::status::in_panes`; the registry is per user, so a Claude in a plain terminal or an abandoned multiplexer would otherwise pin its task's status) merged with its **tmux window's bell flag** (`tmux::signals()`, keyed by slug): any `waiting` → `Blocked` (with Claude's reason), else a bell → `Signaled` (🔔 — any process in any pane can `printf '\a'`; tmux clears it when the window is visited), else any `busy` → `Working`, else a quiet live session → `Done`, none → `Idle`. `Blocked` and `Signaled` are the "needs you" states (`TaskStatus::needs_you`): the watcher notifies on their edge and `sweep` never closes them. **tenx installs no hooks and writes no state of its own**; `tenx hooks install` *removes* the retired v0 hooks. Background agents (`--bg`) run in a subdirectory and are matched by path prefix. The `failed` state was dropped deliberately: the registry can't tell a failed turn from a finished one.
- **The attention watcher** (`cli::watch`): a detached, single-instance process (`~/.config/tenx/watch.pid`) started by `open()`, polling every 2 s (~5 ms per resolve). Two consumers, one resolve pass: a desktop notification on the *edge* into `Blocked` (debounced; tasks already waiting at start are primed as notified; `Done` never notifies — it fires after every turn), delivered via `cli::notify::platform()` (macOS: `terminal-notifier`/`osascript`; Linux: `notify-send`; the mark from `docs/logo/tenx-mark-256.png` is embedded and written to `~/.config/tenx/tenx.png` as the icon, `cli::notify::icon_path`); and `push_status`, which sets `@tenx_status` on each open task window (glyph from `TaskStatus::glyph`, 🔒 when secrets are pending, the bold title, the workspace name muted, then the row's PR/port chips) and the global `@tenx_right` — counting only tasks *other than the current window's*, with `Done` gated on 60 s unanswered so the corner doesn't flicker with every turn you type — only when the digest or the live cache changes, so a quiet session sends nothing. Secrets-pending queues are tracked as further independent edges. Every tick it also publishes the sidebar snapshot (`snapshot::publish`; idle tasks included, unlike the status push). It also gives every background agent (`--bg`, a non-interactive session under a task) a 12-line pane in its task's window, once per (cwd, pid), running `tenx internal agent-log` (`cli::agentlog`) — a compact follower of the agent's transcript that exits with the agent. Exits once the tmux server is gone.
- **`tenx secrets`** (`cli::secrets`): task-scoped credentials via the system `age`/`sops`. Read that module's doc comment before touching it — the invariants (never print a value to stdout; `/dev/tty` reachability decides whether `decrypt`/`set` act or enqueue-and-wait; adopted secrets decrypt outside the worktree and are symlinked in) are the whole design. The no-terminal wait (`wait_for_human`, bounded by `--timeout`, default `DEFAULT_WAIT` = 100 s so a shell tool's 2 min kill never hits first; `--no-wait` to skip) polls the queue and decides fulfilled-vs-withdrawn from output mtimes via `tenx_core::secrets::wait_outcome` — no receipt files. `cancel <name>|--all` (CLI, and `:cancel` in the overlay) only edits the queues.
- **`tenx standup`** (`cli::standup`): prints every `TASK.md` plus user prompts and `git commit`/`git push` calls from `~/.claude/projects/<slug>*/*.jsonl` since the last standup (first `## ` heading in `daily.local.md`, else start of yesterday). Meant to be fed to the `/standup` skill.

## Conventions

- Decision logic goes in `tenx-core` with a test; the binary does I/O.
- Derive state from live sources (disk, the session registry, `tmux list-windows`) rather than recording it; the only tenx-owned per-task files are `.tenx-window-id` (a cache — never act destructively on it, look the window up by slug), `.tenx-pinned`, `.tenx-live.json` (a cache of external facts, written only by the watcher), and the two secrets-pending queues. The one user-level cache is `~/.config/tenx/sidebar.json`, also written only by the watcher, and every reader must cope with it being absent or stale.
- Shell out to the real `git`/`tmux`/`age`/`sops`; never link a library for them.
- Keep `make test` green: clippy runs with `-D warnings`.
